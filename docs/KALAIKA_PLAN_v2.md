## 1. Overview and scope

### 1.1 What the app does
Kalaika is a monthly fee management app for a classical dance teacher (single user in Phase 1). The teacher runs multiple branches. Each branch has multiple batches. Each batch has students. For every month, the teacher marks a student's fee as paid. The app then generates a PDF receipt and opens WhatsApp addressed to the student's registered WhatsApp number, with a pre-written message containing the receipt link. After the teacher sends it, the app records the receipt as sent, and the status updates on screen immediately.

### 1.2 In scope (Phase 1)
- Splash screen and Google sign-in (Firebase Auth)
- Dashboard with month-wise summary across branches and batches
- Create, edit, delete branches
- Create, edit, delete batches inside a branch
- Add students manually, edit, deactivate; import students from an Excel file
- Monthly fee tracker per batch with a month selector
- Mark fee paid: capture amount and payment mode, generate a PDF receipt on the server
- Send the receipt through WhatsApp using a `wa.me` link
- Real-time status updates (unpaid, paid and receipt pending, sent)
- Settings: institute details used on receipts, editable WhatsApp message template, sign out

### 1.3 Out of scope (later phases)
- Automatic WhatsApp sending through the WhatsApp Business API or a provider
- Online payment collection, payment links
- Multiple teachers or staff roles
- iOS release (the code must not block it, but only Android is targeted)
- Attendance, reminders for unpaid fees, push notifications
- Automated tests of any kind

### 1.4 Branding facts (from the admission poster)
- Name: Kalaika, tagline "By Lakshmi Kumaran"
- Dance styles offered: Bharatanatyam, Kuchipudi, Mohiniyattam
- Class modes: Online, Offline, Private
- Contact: 9074283081
- Locations: KMSS Hall, Karumalloor; Sree Kumaramangalam Temple, Paravoothara, N Paravoor

These are used only as defaults (dance style and mode options, default institute details in Settings). All must be editable.

## 2. Architecture and coding standards

### 2.1 Architecture
Use feature-first Clean Architecture with three layers per feature. Dependencies point inward only: presentation depends on domain, data depends on domain, and domain depends on nothing outside Dart.

- **Domain layer** (pure Dart, no Flutter or Firebase imports): entities, abstract repository interfaces, use cases.
- **Data layer**: DTO models (`fromMap`, `toMap`, `toEntity`, `fromEntity`), remote data sources (Firestore, Cloud Functions), repository implementations that map exceptions to failures.
- **Presentation layer**: cubits and their states, pages, feature-specific widgets.

Rules:
- Every user action is a use case: a small class with a single `call` method (for example `RecordPayment`, `MarkReceiptSent`, `ImportStudents`, `WatchMonthlyFees`). Cubits depend on use cases, never on data sources or Firebase types.
- Repositories return `Result<T>`, a sealed class with `Success<T>` and `Err<T>` (holding a `Failure`), defined in `core/`. Do not add an error-handling package. Streams emit `Result<T>` or throw typed failures that the cubit maps to state.
- `Failure` is a sealed hierarchy: `NetworkFailure`, `AuthFailure`, `PermissionFailure`, `NotFoundFailure`, `ValidationFailure`, `ServerFailure`, `UnknownFailure`. Each carries a user-presentable formal message.
- Dependency injection with `get_it`, organized as one registration module per feature, called from `core/di/service_locator.dart`. Repositories and data sources are lazy singletons. Cubits are factories, provided with `BlocProvider` at the route level so they are disposed with the route.
- Navigation only through `go_router`; no `Navigator.push` calls inside widgets other than dialogs and sheets.
- Firebase types (`DocumentSnapshot`, `Timestamp`, `User`) never leave the data layer.

### 2.2 Coding standards
- Lint with `very_good_analysis` (free, MIT). Zero analyzer issues is required at every milestone.
- Null safety strictly: no `dynamic`, no `!` unless immediately justified by a comment, no `late` where a constructor argument works.
- Entities, states and models are immutable (`final` fields, `const` constructors, `Equatable`, hand-written `copyWith`). Do not use code generation (no `freezed`, no `json_serializable`, no `build_runner`).
- Use Dart 3 features where they improve clarity: sealed classes, pattern matching in `switch`, records for small value tuples, enhanced enums.
- One public class per file. File names in `snake_case`; classes in `UpperCamelCase`; suffixes: `_page.dart`, `_cubit.dart`, `_state.dart`, `_repository.dart`, `_repository_impl.dart`, `_model.dart`, `_datasource.dart`, `_usecase.dart` (or the verb name for use cases).
- Widgets: extract UI into widget classes, not helper methods that return widgets. Use `const` constructors everywhere possible. Keep `build` methods under about 80 lines. No business logic, formatting or parsing inside widgets.
- No magic values: spacing in `AppSpacing`, radii in `AppRadius`, durations in `AppDurations`, Firestore collection and field names in `FirestoreKeys`, all UI text in `AppStrings`, all routes in `AppRoutes`.
- Colors and text styles come only from `Theme.of(context)` or the `AppColors` extension; never hard-code a color or font in a widget.
- Public classes and public methods have `///` doc comments. Comments explain why, not what.
- Use `log` from `dart:developer` for diagnostics; never `print`. Never log phone numbers, addresses or other personal data.
- Cancel every `StreamSubscription` and close controllers in `close()`/`dispose()`.
- Prefer small functions with a single responsibility; avoid functions longer than about 40 lines.
- Use `async`/`await` with explicit error handling at the repository boundary. Do not swallow exceptions silently.
- Line length 80 characters, trailing commas on multi-line argument lists, imports ordered: dart, flutter, packages, project (relative imports not used; use `package:` imports).
- Dates are stored as Firestore `Timestamp` in the data layer and `DateTime` in entities. Money is stored as an integer number of rupees (whole rupees only in Phase 1).

## 3. Free-only policy

- Every package must be free and open source (MIT, BSD, Apache-2.0 or similar). Do not use any package that needs a paid licence, a licence key, or has commercial-use restrictions (for example Syncfusion packages are not allowed).

Set `maxInstances` caps on functions and recommend a budget alert in the README.

### 6.11 WhatsApp send flow

Limitation to respect: a `wa.me` link opens a chat with a specific number and a pre-filled text but cannot attach a file. The receipt is therefore delivered as a secure download link inside the message.

Recipient: the student's WhatsApp number. If it is missing or invalid, the send step is replaced by "A valid WhatsApp number is required" with a shortcut to the student edit screen.

Steps:
1. Build the message from the template in Settings (default in 6.13), substituting placeholders.
2. Build the URL: `https://wa.me/<digits>?text=<url-encoded message>` where `<digits>` is the stored international number without a plus sign.
3. Launch with `url_launcher` using `LaunchMode.externalApplication`.
4. If launching fails (WhatsApp not installed), show a dialog with "Copy message" and "Share" options and leave the status as pending.
5. When the app returns to the foreground after launching (a `WidgetsBindingObserver` in the presentation layer), show the dialog: "Was the receipt sent to {recipient name}?" with "Yes, sent" and "Not yet".
   - "Yes, sent": write the sent status (6.12).
   - "Not yet": leave the status as pending; the row keeps its "Send" button.
6. Secondary action "Share PDF" (in the dialog and in the Sent receipt sheet): download the PDF to a temp directory and open the system share sheet with `share_plus`, so the teacher can attach the actual PDF by choosing the contact manually.

Android manifest: internet permission, and a `<queries>` block for `https` VIEW intents and the `com.whatsapp` and `com.whatsapp.w4b` packages so that `canLaunchUrl` works on Android 11 and above.

### 6.12 Marking as sent

### 7.5 `payments/{studentId}_{yyyyMM}`
The document id is deterministic so a month can have only one payment per student and the callable function is naturally idempotent.
```
ownerId: string
branchId: string
batchId: string
studentId: string
studentName: string       // snapshot at payment time
guardianName: string?
whatsappNumber: string
month: string             // "2026-10"
amount: number            // amount recorded for this student for this month
batchFee: number          // snapshot of the batch defaultFee at payment time
mode: string              // cash | upi | bank | other
paidOn: timestamp
note: string?
status: string            // "paid" | "sent" | "voided"   (no document means unpaid)
receiptNo: string         // e.g. "KLK-2026-000123"
receiptPath: string       // Cloud Storage path
receiptUrl: string        // tokenized download URL
sentAt: timestamp?
sentVia: string?          // "wa_me"
voided: bool              // default false
createdAt: timestamp
```

The "Receipts pending" list uses a collection group query on `payments` with `ownerId == uid`, `month == selected`, `status == "paid"`. Add the required composite index.

### 7.6 `summaries/{yyyyMM}` (written only by Cloud Functions)
```
month: string
collected: number
paidCount: number
sentCount: number
byBatch: {
  "<batchId>": { branchId: string, collected: number, paidCount: number, sentCount: number }
}
updatedAt: timestamp
```

Expected totals and student counts come from the batch and branch documents, so the dashboard computes pending amounts as `expectedMonthlyTotal - collected` without reading students.

## 8. Security rules and indexes

### 8.1 Firestore rules (intent)
- Everything under `users/{uid}` is readable and writable only when `request.auth.uid == uid`, with these exceptions:
  - `payments`: clients may read; may not create or delete; may update only to change `status` from `paid` to `sent` together with `sentAt` and `sentVia`, and no other field.
  - `summaries` and `meta`: clients may read `summaries`; no client writes to either.
- Basic validation on branch, batch and student writes (non-empty names, `monthlyFee` and `defaultFee` positive numbers, `whatsappNumber` non-empty).

### 8.2 Storage rules
Deny all client reads and writes. Receipts are written by the Cloud Function through the Admin SDK and are reached through the tokenized download URL in the message.

### 8.3 Indexes (`firestore.indexes.json`)
- Collection group `payments`: `ownerId`, `month`, `status` (all ascending)
- Collection group `batches`: single-field index on `ownerId` with collection group scope
- `payments` within a batch: `studentId` ascending, `month` descending
- `students` within a batch: `isActive` ascending, `fullName` ascending

## 9. Cloud Functions

Location: `functions/` (TypeScript, strict mode). Region `asia-south1`. Use v2 APIs. Structure the code in modules: `callables/`, `triggers/`, `services/` (pdf, storage, counters), `validators/`, `config/`. Use ESLint with the TypeScript recommended rules (free).

### 9.1 Callable: `generateReceipt`

Input:
```
{ branchId, batchId, studentId, month: "yyyy-MM", amount: number, mode: string, paidOn: ISO string, note?: string }
```

Behavior:
1. Reject if the caller is not authenticated. Derive `uid` from the auth context, never from the payload.
2. Validate the payload (month format, amount greater than zero, mode in the allowed list).
3. Load the student, batch, branch and the user's institute settings. Reject if any is missing.
4. Idempotency: if `payments/{studentId}_{yyyyMM}` exists and is not voided, return its existing `receiptNo` and `receiptUrl` without creating another.
5. In a Firestore transaction: increment `users/{uid}/meta/counters.receiptSeq` and create the payment document with `status: "paid"`, the submitted `amount`, a `batchFee` copied from the batch's current `defaultFee`, and a generated `receiptNo` in the format `KLK-{year}-{6-digit sequence}`. If the document was voided earlier, reuse it and issue a new receipt number.
6. Generate the PDF (9.2) and upload it to `receipts/{uid}/{yyyyMM}/{receiptNo}.pdf` with a random `firebaseStorageDownloadTokens` metadata value.
7. Update the payment document with `receiptPath` and `receiptUrl`, built as `https://firebasestorage.googleapis.com/v0/b/{bucket}/o/{encodedPath}?alt=media&token={token}`.
8. Return `{ receiptNo, receiptUrl, status: "paid" }`.

If PDF generation or upload fails after the transaction, delete the payment document so the row returns to unpaid, then throw an `HttpsError`.

### 9.2 PDF receipt (pdf-lib)
- A4 portrait, dark text on white so it prints well; copper and gold only for accents (a thin header rule, the institute name).
- Embed Google Fonts through `@pdf-lib/fontkit`: bundle Noto Sans (Regular, Bold) and Cinzel (Bold) `.ttf` files under `functions/assets/fonts/`. The standard PDF fonts cannot render the rupee symbol, so embedded fonts are mandatory.
- Layout:
  1. Header: institute name (Cinzel, copper), tagline, address and phone
  2. Title "FEE RECEIPT" with receipt number and date at the right
  3. Details table: received from (guardian name, or the student's full name when no guardian is recorded), student full name, branch, batch, dance style, month and year, payment mode, paid date
  4. Amount box with the amount in figures and in words
  5. Note line if present
  6. Footer: "Received with thanks", signatory name, footer note, and "This is a computer generated receipt."
- Format currency with Indian digit grouping (for example 12,500).

### 9.3 Firestore trigger: `onPaymentWritten`
Triggered on any write to `users/{uid}/branches/{branchId}/batches/{batchId}/payments/{paymentId}`. Compute the difference between the before and after states (paid, sent, voided) and apply `FieldValue.increment` updates to `users/{uid}/summaries/{yyyyMM}` for `collected`, `paidCount`, `sentCount` and the `byBatch.<batchId>` counters, using `set` with `merge: true`. Ignore writes that change nothing relevant so duplicate invocations are harmless.

### 9.4 Callable: `voidPayment`
Input: `{ branchId, batchId, studentId, month }`. Marks the payment `voided: true` and `status: "voided"`, keeps the receipt number and file for audit, and allows the month to be paid again. The trigger in 9.3 reverses the summary counts. The Fees tab row returns to Unpaid.

### 9.5 Operational notes
- Set `maxInstances` to a small value (for example 5).
- Log with `functions.logger`; never log phone numbers or addresses.
- `firebase.json` must configure the emulators (Firestore, Functions, Storage) for development.

## 11. Excel import specification

### 11.1 Expected file
A `.xlsx` file, first sheet, first non-empty row is the header. Header matching is case-insensitive and ignores extra whitespace. The columns available in the teacher's sheet are:

| Column | Required | Accepted header variants |
|---|---|---|
| Full Name | yes | "Full name", "Name", "Student Name" |
| Phone Number | no | "Phone", "Phone no", "Mobile" |
| WhatsApp Number | yes (see rule below) | "WhatsApp", "WhatsApp no" |
| Date of Birth | no | "DOB" |
| Age | no | |
| Guardian | no | "Guardian Name", "Parent" |
| Guardian Phone Number | no | "Guardian Phone", "Guardian Contact" |
| Address | no | |

There is no fee column. Every imported student receives the batch default fee as `monthlyFee`, editable later.

Provide a "Download sample template" button that generates a sample `.xlsx` with these headers (using the `excel` package) and opens the share sheet.

### 11.2 Row rules
- Full Name is required; a blank name makes the row invalid.
- WhatsApp Number is required. If it is blank but Phone Number is present, use the Phone Number as the WhatsApp number and flag the row with a warning. If both are blank or invalid, the row is invalid.
- Date of Birth accepts Excel date cells, `dd/MM/yyyy`, `dd-MM-yyyy` and `yyyy-MM-dd`. An unparseable value makes the row invalid with a clear reason.
- Age: when a valid Date of Birth exists, the age is derived from it and the sheet's Age is ignored. Otherwise the sheet's Age is stored if it is an integer from 1 to 100.
- Phone, WhatsApp and Guardian Phone are normalized with the rules in 11.4. An invalid optional number (Phone, Guardian Phone) is dropped with a warning; it does not invalidate the row.
- Cell text is trimmed. Numbers stored as text or as scientific notation by Excel are converted to plain digit strings.

### 11.3 Flow
1. Pick the file with `file_picker` (allowed extension `xlsx`). If `.xls` is selected, show a message asking the user to save it as `.xlsx`.
2. Parse off the UI thread (`compute` or an isolate). Cap at 1000 rows.
3. Validate each row and show a preview with filters: Valid, Warnings, Needs correction, Duplicates, with counts at the top.
4. Duplicates are detected within the file (same normalized WhatsApp number and same lower-cased full name) and against students already in the batch (load the batch's students once).
5. The user imports the valid rows (including rows with warnings). Rows needing correction and duplicates are skipped and listed in the result summary.
6. Write in chunks of at most 400 student documents per `WriteBatch` (the Firestore limit is 500 writes, leaving headroom). After all chunks succeed, apply one update to the batch document (`studentCount`, `expectedMonthlyTotal` with `FieldValue.increment`) and one to the branch document (`studentCount`).
7. Show progress (chunks completed over total) and a final summary: imported, skipped, failed. If a chunk fails, stop, report how many were saved, and let the user retry the remainder; the duplicate check prevents double entries.

### 11.4 Phone normalization (`phone_utils.dart`)
- Strip spaces, dashes, parentheses and a leading plus sign.
- 10 digits: prefix `91`.
- 11 digits starting with `0`: drop the zero, prefix `91`.
- 12 digits starting with `91`: accept.
- Other lengths from 11 to 15 digits: accept as an international number only after the user confirms on the single-student form; in bulk import mark as needs correction.
- Anything else is invalid.
- Store digits only (for example `919074283081`); display as `+91 90742 83081`.

## 12. Error handling and edge cases

- No network: Firestore offline persistence lets reads work from cache. Disable "Confirm and generate receipt" while offline with a formal message, since the function call needs a connection.
- Double taps: disable the control while a request is in flight; the function is idempotent as a second safeguard.
- Student without a valid WhatsApp number: payment can be recorded, but the send step shows "A valid WhatsApp number is required" with a shortcut to edit the student.
- A student added after a month begins appears as unpaid for that month.
- Deactivated students are excluded from the tracker and from expected totals (counters are decremented on deactivation).
- Changing a student's fee or the batch fee affects only future payments; recorded payments keep their stored `amount` and `batchFee`. Resending a message for an existing payment is built from the stored payment values, not from the current batch or student fee.
- Sign-out clears cubit state and cancels all subscriptions.
- Time zone: all months are treated as Asia/Kolkata local time. Month keys are computed on the device from the selected month, not from server time.
- Every failure shown to the user uses formal wording from `AppStrings` (for example "The receipt could not be generated. Please try again.").

## 13. Cost-control rules (hard requirements)

1. No per-student reads on the dashboard. It reads the single summary document for the month, the branch list and one collection group query for batches.
2. The fee tracker uses exactly two listeners: the batch's active students and the batch's payments for the selected month. Never run a query per student.
3. Attach snapshot listeners only to the visible screen and cancel them on leave.
4. Every list that can grow (student history) uses `limit`.
5. Counters and rollups use `FieldValue.increment` and Cloud Functions, never collection scans.
6. Student import uses chunked batch writes and a single read of existing students for duplicate detection.
7. Functions use `maxInstances` caps and do minimal reads.
